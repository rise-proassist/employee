== 調査対象と前提

- 調査対象: `backend/` 配下（`backend/controller` と `backend/admin/controller`）
- ルーティング方式: `/{controller}/{action}/`（`action` 省略時は `index`）
- 実行入口:
	- 従事者サイト: `backend/htdocs/index.php`
	- 管理サイト: `backend/admin/htdocs/index.php`
- 本ドキュメントは「フロントエンドから利用可能なエンドポイント」を優先列挙
- `BK/` 配下は旧実装として除外

== ルーティング仕様（実装ベース）

=== 従事者サイト (`backend/core/classes/Dispatcher.php`)

- URL解析: `$_SERVER['REQUEST_URI']` を `/` 分割
- `params[1]` を controller として採用（未指定時 `top`）
- `params[2]` を action として採用（未指定時 `index`）
- 実行メソッド: `{action}Action`

=== 管理サイト (`backend/admin/core/classes/Dispatcher.php`)

- 基本仕様は同様
- デフォルト controller は `top`

== 認証境界（Frontend設計で重要）

- `MypageController`: セッションログイン必須（未ログイン時 `/login/` へ遷移）
- `LoginController`, `AccountController`, `TopController`, `NewsController`, `EtcController`: 非ログインでもアクセス可能
- `ApiController`（従事者側）: 原則未認証でも到達可能だが、`generateQr`/`generateBar` はセッション `user` が必要
- 管理API (`backend/admin/controller/ApiController.php`): CSRFトークン検証あり（POST）

== 3) フロント実装向け補足

- 現状バックエンドは「画面遷移 + フォームPOST」中心で、JSON API は限定的。
- React再構築では、まず既存画面フローを上記エンドポイントに合わせて実装し、必要に応じて専用JSON APIを追加する段階移行が現実的。
- `entryAccept/entryDeny` は参照DAOが現行ツリーに見当たらず、利用する場合はバックエンド側の整合性確認が必要。
